# bento-tools 3.0 design plan

This document is the planning artifact for [ckmah/bento-tools](https://github.com/ckmah/bento-tools). It uses [YeoLab/bento-tools](https://github.com/YeoLab/bento-tools) v2.1.4.post2 as historical reference only. Version 3.0 is a clean break, not a port.

## Executive summary

bento-tools 2.x is a scanpy-style toolkit for subcellular spatial omics on `SpatialData`. It no longer installs cleanly on current Python and scverse stacks (measured 2026-10-19), and its bundled fixtures fail `TableModel` validation on `spatialdata` 0.4+.

**Version 3.0** centers on **RNAflux**, **shape-derived features**, and **point features** inside segmented instances, with APIs and internals that work in **2D and 3D** (same function signatures; coordinate dimension inferred from `SpatialData` elements). **RNAforest** (`lp`, models, training assets, and related plots) is removed. **GPU is optional**; **CPU is the default and the CI truth**. Plotting defers to **`spatialdata-plot`** except where bento-specific encodings (flux embeddings, fluxmap domains) require custom code. Distribution stays **`bento-tools` on PyPI** with **`import bento as bt`**. There are **no 2.x migration shims**; users clean-install 3.0.

Subcellular **gene-pair interaction** statistics (ligand-receptor-style branding, within-cell scope) are **not in 3.0.0**; algorithm options live in [`docs/3.0-algorithms.md`](3.0-algorithms.md) for iteration. Legacy CLQ/tensor colocation are reference only.

Delivery is a greenfield package in ckmah/bento-tools plus the phased PR queue below. **Algorithm goals** are iterated in `3.0-algorithms.md` before implementation PRs land.

| GPU | **Optional** extra; **CPU default** for every public API. |
| Plotting | **`spatialdata-plot` first**; keep only bento-specific plots. |
| Package names | PyPI **`bento-tools`**, import **`bento`**. |
| 2.x compatibility | **None.** Clean install; no `migrate` helpers. |
| Instance IDs | Follow **`spatialdata` `TableModel`** linking (`region`, `region_key`, `instance_key`); align with scverse tutorials and squidpy-on-`SpatialData` workflows (citations below). |

### Instance and region IDs (spatialdata / squidpy convention)

bento does not define a parallel ID scheme. It consumes whatever `TableModel.parse()` accepts and what downstream scverse tools expect.

From the [SpatialData “from scratch” tutorial](https://spatialdata.scverse.org/en/latest/tutorials/notebooks/notebooks/examples/sdata_from_scratch.html):

- **`region`** in `adata.uns["spatialdata_attrs"]` names the annotated element(s) (shapes, labels, points).
- **`region_key`** is an `obs` column (typically **categorical**) whose values select which element each row annotates.
- **`instance_key`** is an `obs` column whose values **match the index** of that element (shapes GeoDataFrame index, labels object, etc.).
- Each **`(region_key, instance_key)` pair must be unique** within the table; **`instance_key` values need not be globally unique** across regions ([spatialdata-io discussion #203](https://github.com/scverse/spatialdata-io/issues/203)).

The tutorial example uses **integer** `spot_id` aligned with `shapes.index`. **Integer instance IDs** are the default for segmentation masks and cell polygons. **String** IDs (including pandas `StringDtype` on newer `spatialdata`) are valid when they match the element index ([spatialdata PR #1063](https://github.com/scverse/spatialdata/commit/cd8546a790f7c4b9d1a20216c49182290ee524a6)).

**bento 3.0 rules:**

1. Never coerce instance IDs to a dtype that fails `TableModel.validate` (avoid ad hoc `str` indices on shapes without matching `obs`).
2. Use `TableModel.parse(..., region=, region_key=, instance_key=)` when building or rebuilding the count table in `pp.prep`.
3. For point-to-instance assignment, store instance IDs in points columns using the **same values** as the linked shape/labels index, not a separate naming scheme.
4. **squidpy** does not replace this metadata; it operates on `AnnData` / `SpatialData` already wired this way. Connectivity plotting remains squidpy’s domain ([spatialdata-io #203](https://github.com/scverse/spatialdata-io/issues/203)).

Gene-pair / colocation direction is documented in [`docs/3.0-algorithms.md`](3.0-algorithms.md) (§A). Implementation waits on Clarence’s algorithm choices.

## Dimension-agnostic data model

**Container:** validated `SpatialData` only. No wrapper type.

**Coordinate dimension:** Read from element models (`PointsModel`, `ShapesModel`, `Labels2DModel` / `Labels3DModel`, images). Expose `bento.pp.spatial_dims(sdata, element_key) -> tuple[str, ...]` (e.g. `("x", "y")` or `("x", "y", "z")`). All `tl` functions accept the same kwargs; **raise a clear error** if a method is called on unsupported geometry (e.g. 2D-only raster flux on pure 3D mesh without voxels).

| Core shape | Role |
|------------|------|
| **SpatialData** | On-disk (Zarr) and in-memory container |
| **InstanceTable** | `AnnData` via `TableModel` (`region`, `region_key`, `instance_key`) |
| **TranscriptPoints** | Points element with `feature_key` + per-region instance columns |
| **RegionGeometry** | **2D:** `ShapesModel` polygons. **3D:** `Labels3DModel` (instance IDs in a `(z, y, x)` or `(z, x, y)` label image per SpatialData axes). No triangular mesh storage in SpatialData. |
| **BentoResults** | `InstanceTable.uns["bento"]` versioned dict (`schema_version: 1`) for flux, features, comp |
| **NeighborhoodIndex** | Optional shared structure in `uns["bento"]` for KNN/ball queries (2D/3D) |

**2D vs 3D algorithm notes:**

| Capability | 2D | 3D |
|------------|----|----|
| Shape metrics (area, perimeter, …) | Shapely polygons | Volume and surface area from **3D label masks** (`skimage.measure` on cropped instance voxels) |
| Point-in-instance | `sjoin` / point-in-polygon | **Voxel lookup** in 3D label image (or `z` slice + 2D labels if data are stored per-section) |
| Proximity / distance features | Boundary distance in plane | **Euclidean distance transform** on instance mask (isotropic voxels; see locked Δz = Δx = Δy default) |
| Ripley / L-function | 2D point patterns | **3D Ripley** (different null; optional feature, not required for 3.0.0) |
| RNAflux raster | 2D grid per cell in **physical units** | **3D isotropic voxel grid** per cell; default **equal spacing** on x, y, z; resample anisotropic source data to isotropic voxels in `pp.prep` when metadata supplies z spacing |
| Plotting | `spatialdata-plot` | Same; 3D may need napari for inspection (document, not required in CI) |

**Results storage:** Cell-level matrices in `obsm` when shape is `(n_instances, k)`; tables and flux metadata in `uns["bento"]`. Point-level flux columns remain on the points element only when needed for plotting.

## Performance strategy

- **Default backend:** CPU (NumPy, SciPy, Numba `prange` for per-instance loops).
- **Optional GPU:** `bento-tools[gpu]` with CuPy (and optionally cuML for neighbors). Same API via `bt.config(backend="cpu"|"gpu"|"auto")`; CI never depends on GPU.
- **Shared neighbor index** for flux (and future CLQ): one build per `(points, instance_key, radius|knn)` per dimension.
- **Engineering goal (estimated, not measured):** order-of-magnitude speedup on flux and point features at 10k+ cells after prep rewrite and Numba; record real benchmarks in PR-03 fixtures notebook.

## Proposed 3.0 public API sketch

```
bento/
  config.py            # backend, n_jobs, rng
  pp/                  # prep, validate, filter_by_gene, spatial_dims
  tl/                  # flux, features, comp, results accessor
  pl/                  # flux, fluxmap, fe + spatialdata-plot helpers
  datasets/
  platforms/
  backends/            # numpy/cupy (internal)
```

**`bt.pp`:** `prep`, `validate`, `filter_by_gene`, `spatial_dims`

**`bt.tl`:** `analyze_shapes`, `shape_stats`, `analyze_points`, `list_*`, `register_*`, `flux`, `fluxmap`, `fe`, `load_gene_sets`, `comp`, `comp_diff`, `results(sdata)`

**`bt.pl`:** `render_flux`, `render_fluxmap`, `render_fe` (names TBD); re-export or thin-wrap `spatialdata-plot` for `points` / `shapes` / `labels` where possible

**Not in 3.0.0:** `lp*`, `coloc_quotient`, `colocation`, `bt.ut`, per-feature shape one-offs, import-time colormaps

## What changed from 2.x (no migration path)

Version 3.0 is a **new major** on a clean branch. Users should **uninstall 2.x**, install 3.0, and rebuild notebooks from current `SpatialData` objects.

- **Removed:** RNAforest (`bt.tl.lp` and related), `bt.ut`, bundled RF models, colocation APIs in the initial 3.0.0 release, most standalone `bt.pl` mirrors of scverse plotting.
- **Renamed / reorganized:** `bt.io.prep` → `bt.pp.prep`; results live under `table.uns["bento"]` with a schema version.
- **Stricter data:** Tables must satisfy `TableModel` (`region`, `region_key`, `instance_key`); instance columns must match spatial element indices per SpatialData docs.
- **New capability:** First-class **3D** points and segmentations where algorithms support them.
- **PyPI name unchanged:** `pip install bento-tools` still provides `import bento`.

## Design alternatives (remaining)

### GPU stack

**Decision:** optional CuPy/cuML; CPU default (locked). JAX and mandatory RAPIDS rejected for install weight and geospatial fit.

### Container type

**Decision:** pure `SpatialData` + `pp.validate` (unchanged).

## Risks

| Risk | Mitigation |
|------|------------|
| 3D flux memory | Chunked voxels, per-instance bounds, documented limits |
| 3D feature scope creep | Ship 3D distances + label-based metrics in 3.0.0; defer exotic 3D Ripley |
| scverse API churn | Pin `spatialdata>=0.8`; weekly compat job |
| Gene-pair scope creep | Keep 3.0.0 to signed algorithms in `3.0-algorithms.md` |
| GPU bitrot | GPU extras smoke-tested manually; CPU is merge gate |
