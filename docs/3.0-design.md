# bento-tools 3.0 design plan

This document is the planning artifact for [ckmah/bento-tools](https://github.com/ckmah/bento-tools). It uses [YeoLab/bento-tools](https://github.com/YeoLab/bento-tools) v2.1.4.post2 as the behavioral reference. It does not require a line-by-line port of 2.x.

## Executive summary

bento-tools 2.x is a scanpy-style toolkit for subcellular spatial transcriptomics built on `SpatialData`. The code still carries packaging drift (Hatch/Rye vs Poetry publish), dependency pins that block current Python and scverse releases, and a data contract that no longer passes `spatialdata` 0.4+ validation. On a fresh Python 3.11 environment with `spatialdata` 0.4.0 (measured 2026-10-19), the bundled `small_data.zarr` fails at `read_zarr`, and `bt.io.prep` fails at `aggregate` when rebuilding the count table.

3.0 should treat **valid `SpatialData` + `TableModel` annotations** as the only supported input, store algorithm outputs in a **small, versioned results schema** instead of ad hoc `AnnData.uns` keys, and expose a **smaller public API** (`io`, `pp`, `tl`, `pl`, `datasets`) with the same scientific scope where it still earns its place (RNAforest localization patterns, RNAflux, colocalization quotient, composition). Performance work should center on **neighbor queries and per-cell Python loops**, with one **array backend** (NumPy by default, optional CuPy) rather than separate code paths per algorithm.

Delivery should land as a **greenfield package layout** in ckmah/bento-tools, with a phased PR queue below. Most phases can run in parallel once the scaffold and data contract exist.

### Dependencies and scverse compatibility

Runtime pins in 2.x conflict with a current scverse stack (PyPI latest versions checked 2026-10-19: `spatialdata` 0.8.0, `anndata` 0.13.4, `scanpy` 1.12.4, `squidpy` 1.8.3).

| `shapely~=2.0.1` | Narrow pin | Unnecessary with current GEOS wheels. |

| `sparse` | Direct dep | Used only for dense tensor materialization in colocation; replaceable. |
| `emoji` | Direct dep | User-facing prints in `tl`; not appropriate for library core. |
| `torch` | Optional extra | **Not imported anywhere** in 2.x Python sources (inferred from repo search). |
| `decoupler` | Direct dep | Only pathway enrichment wrapper for `fe()`. |
| `geopandas`, `dask`, `anndata` | Transitive | Heavily used; should be explicit lower bounds aligned with `spatialdata`. |

Docs drift: `installation.md` mentions Python 3.9 and `pip install ".[torch]"` while extras are named `extras` in `pyproject.toml`.

**Inferred hotspots** (from static review of 2.x; rank by expected cost at Xenium-scale cell counts):

1. **`coloc_quotient`**: one Python task per cell via `dask.bag`, each calling `sklearn.neighbors.NearestNeighbors` and pandas groupby (`bento/tools/_colocation.py`). Cost scales with **cells × (neighbor query + gene pair stats)**.
2. **`analyze_points` / RNAforest `lp`**: per-cell, per-gene-group feature computation with repeated `get_points(..., sync=True)` materialization (`bento/tools/_point_features.py`, `bento/tools/_lp.py`).
3. **`flux`**: rasterization and neighborhood accumulation per cell (`bento/tools/_flux.py`, `rasterio.features`, sparse vstack loops).
4. **`io.prep`**: repeated spatial joins and full `aggregate` count rebuild (`bento/io/_index.py`, `bento/io/_io.py`).
5. **`colocation` tensor build**: `sparse.COO(...).todense()` materializes a **dense** 3D tensor (`bento/tools/_colocation.py`).

Squidpy and scanpy already cover **tissue-level** neighbors, co-occurrence, and generic plotting. bento should not duplicate those. It should own **within-cell** subcellular statistics and the RNAforest / RNAflux / CLQ methods.

### Data model today (2.x)

**Container.** Everything is a `spatialdata.SpatialData` object after `prep`.

**Core shapes (names for 3.0 docs):**

| Shape | 2.x location | Content |
|-------|----------------|---------|
| **Transcript points** | `sdata.points[points_key]` | Columns: `x`, `y`, `feature_key`, per-shape instance columns, optional groupby cols. |
| **Region geometries** | `sdata.shapes[shape_key]` | GeoDataFrame; index = instance id (forced to `str` in prep). |
| **Cell-by-gene counts** | `sdata.tables["table"]` | `AnnData` from `TableModel.parse` after `aggregate(..., aggfunc="count")`. |
| **Algorithm payloads** | `sdata.tables["table"].uns[...]` | `lp`, `lpp`, `clq`, `tensor`, `factors`, `comp_stats`, dynamic `*_features` keys. |
| **Per-point derivatives** | points columns via `set_points_metadata` | e.g. flux rasters, fluxmap labels. |

**Pain points.**

- Instance ids are **strings in shapes** but `TableModel` in modern `spatialdata` expects **integer or object-dtype string** instance columns, not pandas `string` dtype (measured validation errors).
- Results in `uns` are **unversioned** and collide with non-bento keys.
- `prep` always **rebuilds** the count table and mutates multiple elements, which is expensive and hard to compose with upstream pipelines.

### Proposed 3.0 data model

**Principle:** bento does not invent a parallel container. It reads and writes **validated `SpatialData`**, and stores bento-specific outputs in a **single versioned bucket** with typed views.

**Required input contract (`bento.pp.validate` or `prep`):**

- `points[points_key]` with coordinates and `feature_key` in attrs.
- `shapes[instance_key]` with stable **instance id** compatible with `TableModel` (document int vs str choice; default **integer `obs` instance column** for new tutorials).
- Optional `tables["table"]` if pre-aggregated; otherwise bento builds it once via `spatialdata.aggregate`.

**Named core shapes:**

| Name | Type | Description |
|------|------|-------------|
| `SpatialData` | container | Canonical object on disk (Zarr) and in memory. |
| `CellTable` | `anndata.AnnData` | Rows = cells/instances; `X` = gene counts; `obs` holds `region`, instance id, phenotype columns. |
| `TranscriptPoints` | `dask.dataframe.DataFrame` or `pandas.DataFrame` | Subcellular point cloud with instance assignment column per region. |
| `BentoResults` | `CellTable.uns["bento"]` (dict v1) | Version key `schema_version: 1`; sub-keys `lp`, `flux`, `clq`, etc. as `DataFrame` / `numpy` / sparse arrays with documented shapes. |
| `NeighborhoodIndex` | optional cached object | Shared spatial index (scipy `cKDTree`, `sklearn` NN, or GPU equivalent) keyed in `uns["bento"]["neighbors"]` to avoid rebuilding per method. |

**Writes.** Functions return **views or copies** where practical (`return_sdata=False` default mutates for notebook ergonomics; `True` for pipelines). Prefer writing cell-level matrices to **`obsm`** when dimensions are `(n_cells, k)` and tables to **`uns["bento"]`** for metadata-rich frames.

### Performance strategy

**Goals.** Same API on CPU by default; optional GPU via config or context manager. Target **10×–100×** on CLQ and point features for 10k+ cells (estimated engineering goal, not measured).

| Layer | CPU | GPU (optional) |
|-------|-----|----------------|
| Array math | NumPy, SciPy sparse | CuPy + cuPy-compatible paths |
| Neighbor search | `sklearn.neighbors`, `scipy.spatial.cKDTree` | `cuml.neighbors.NearestNeighbors` or cupyx when RAPIDS available |
| Per-cell loops | **Numba** `prange` over cells | Numba CUDA only where maintenance is justified; else batch on GPU NN |
| Table aggregations | Polars lazy frames or pandas 2 pyarrow backend | cuDF via optional extra |
| Tensor decomposition | `tensorly` CPU | `tensorly` with CuPy backend when installed |

**API sketch.**

```python
import bento as bt

with bt.config(backend="cpu"):  # or "gpu", "auto"
    bt.tl.coloc_quotient(sdata, ...)
```

**Do not** require GPU for install. Extras: `bento-tools[gpu]` → `cupy-cuda12x` or documented RAPIDS meta-package.

**Benchmark plan for implementation phase** (not run in this doc pass). Use a public Xenium tiny crop or refreshed `small_data` with **measured** cell count, transcript count, gene count, hardware, and package versions recorded per `benchmark-checklist`. Primary metrics: wall time for `prep`, `lp`, `coloc_quotient`, `flux` on fixed hardware; memory high-water mark for colocation tensor step.

## Proposed 3.0 public API sketch

```
bento/
  __init__.py          # version, config, re-exports
  config.py            # backend, n_jobs, random_state
  io/                  # read/write helpers (thin)
  pp/                  # prep, validate, filter_by_gene
  tl/                  # analysis (below)
  pl/                  # domain plots
  datasets/
  platforms/           # CosMx, Xenium pixel constants
  backends/            # numpy/cupy dispatch (internal)
```

**`bt.pp`**

- `prep(sdata, *, points_key, feature_key, instance_key, regions, rebuild_table=...)`
- `validate(sdata, ...) -> BentoValidationReport`
- `filter_by_gene(sdata, genes)`

**`bt.tl`**

- Shape: `analyze_shapes`, `shape_stats`, `register_shape_feature`, `list_shape_features`
- Point: `analyze_points`, `list_point_features`, `register_point_feature`
- RNAforest: `lp`, `lp_stats`, `lp_diff_discrete`, `lp_diff_continuous`
- RNAflux: `flux`, `fluxmap`, `fe`, `load_gene_sets`
- Spatial stats: `coloc_quotient`, `colocation`, `comp`, `comp_diff`
- Accessors: `bt.tl.results(sdata)` → read-only `BentoResults` wrapper

**`bt.pl`**

- `points`, `density`, `shapes`, `flux`, `fluxmap`, `fe`, `colocation`, `factor`, `lp_*`, `comp`, `shape_stats`

**Removed from public top level:** `bt.ut`, per-feature shape functions, concrete `PointFeature` classes, import-time colormap registration.

## Breaking changes and migration

1. **Python 3.10** dropped if required by NumPy 2 / `spatialdata` 0.8.
2. **`bt.ut`** removed. Use `bt.pp` and `bt.tl.results`.
3. **Results keys** move from scattered `table.uns` names to `table.uns["bento"]` with version field. Provide `bento.migrate.sdata_v2_to_v3(sdata)` in PR-14.
4. **Shape feature functions** (`bt.tl.area`, etc.) removed. Use `analyze_shapes(..., features=["area"])`.
5. **Import side effects** (`bt.colors`) removed. Call `bt.pl.register_colormaps()` explicitly.
6. **Instance id dtype** may change from arbitrary strings to int or `object` str. Migration doc lists `obs` column coercion.
7. **Optional extras** renamed: `extras` → `gpu` / `enrichment` / `docs`.

Migration story for notebooks: run `migrate`, re-run `pp.prep` once, re-run analyses (results not binary portable due to model and dtype fixes).

## Design alternatives (contested choices)

### A. Container wrapper type vs pure SpatialData

| Option | Pros | Cons |
|--------|------|------|
| **Pure SpatialData** (recommended) | Full scverse interoperability, simpler mental model | Less compile-time enforcement |
| **`BentoData` wrapper** | Can enforce invariants | Friction with scanpy/squidpy, another object to learn |

**Recommendation:** Pure `SpatialData` plus `pp.validate` and `tl.results` accessor.

### B. GPU stack

| Option | Pros | Cons |
|--------|------|------|
| **CuPy dispatch** in shared kernels | One code path with array module swap | No NN on GPU without extra libs |
| **RAPIDS cuML / cuDF** | Fast NN and groupby at scale | Heavy install, CUDA version coupling |
| **JAX** | Portable autodiff | Poor fit for geospatial joins; high rewrite cost |

**Recommendation:** NumPy + Numba on CPU; optional `cupy` for array-heavy steps; optional `cuml` documented in `[gpu]` extra for neighbor search only.

### C. RNAforest model format

| Option | Pros | Cons |
|--------|------|------|
| **Retrain sklearn / xgboost** export with version metadata | Keeps tree model interpretability | Needs labeled training data refresh |
| **ONNX runtime** | Faster inference | New dependency; retrain pipeline |
| **Drop RNAforest** | Saves maintenance | Loses flagship method |

**Recommendation:** Retrain with sklearn 1.5+ or xgboost; store model in `bento/models/` with manifest; keep method.

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| scverse API churn | Breaks `prep` / `aggregate` | Pin lower bound; weekly cron job against `spatialdata` main |
| No measured 2.x baseline on modern stack | Wrong perf priorities | PR-03 + benchmark notebook before optimizing |
| RNAforest retrain drift | Science regression | Golden tests on fixed fixture probabilities |
| GPU optional path bitrots | User confusion | CPU path is CI truth; GPU smoke weekly only |
| Scope creep into squidpy | Duplicate ecosystem | Document "within-cell only" boundary in README |

## Open questions for Clarence (product)

1. **Scope:** Is RNAflux + fluxmap still a flagship for 3.0, or can flux ship in 3.1 while LP + CLQ ship first?
2. **GPU:** Is optional CUDA enough, or is RAPIDS a hard requirement for a lab deployment?
3. **Plotting:** Should bento own matplotlib domain plots long term, or push more to `spatialdata-plot` callbacks only?
4. **PyPI name:** Stay `bento-tools` with import `bento`, or rename package for the 3.0 marketing cut?
5. **2.x maintenance:** Security fixes only on 2.x branch, or full parallel support during migration?
6. **Training data:** Is there an updated labeled set for RNAforest beyond 2022 pickles, or should 3.0 ship the old model with documented limits?
7. **Cell id convention:** Prefer integer instance ids (squidpy-like) or string barcodes from vendors?
